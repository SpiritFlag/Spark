# ✨ Spark

**함께 생각하고, 자유롭게 만들고, 실제 결과로 판단하는 AI 개발 방식.**

Spark는 개발자가 AI와 함께 소프트웨어를 만드는 가벼운 협업 방식입니다.

개발자는 아이디어를 구상하고, 기술적인 선택을 토론하며, 결과물을 직접 평가합니다. AI는 코드 조사, 구현, 반복 작업, 검증을 수행하면서 개발자의 동료로 참여합니다.

Spark의 목표는 개발자를 대신해 모든 것을 결정하는 것이 아닙니다.

**개발자가 직접 코드를 타이핑하지 않아도, 여전히 개발의 중심에 있을 수 있도록 하는 것.**

## 🚗 개발 흐름

| 단계 | 무엇을 하나요? | 주로 사용하는 환경 |
|---|---|---|
| **Plan** | 자유롭게 아이디어를 구상하고 발전시킵니다. | ChatGPT |
| **Design** | 코드베이스를 조사하고 기술적 구현 방향을 토론합니다. | Codex |
| **Implement** | 실제로 만들고, 실행하고, 피드백을 반영합니다. | Codex |
| **Deploy** | 빌드·머지·배포·릴리즈와 문서 정리를 수행합니다. | Codex |

네 단계는 작업을 이해하기 위한 구분이지, 반드시 모두 거쳐야 하는 절차는 아닙니다.

작은 수정은 바로 구현할 수 있고, 구현 도중 기술적인 고민이 생기면 다시 Design을 논의할 수도 있습니다.

단계 사이의 맥락은 임시 Handoff 문서로 전달합니다.

## 📚 프로젝트 문서

Spark는 두 개의 영구 문서를 사용합니다.

### VISION.md — 무엇을 만들고 싶은가?

사람이 읽는 제품 구상서입니다.

- 프로젝트를 시작한 이유
- 제품의 목적과 핵심 가치
- 기대하는 사용자 경험
- 중요한 기획적 결정과 방향

오랜 시간이 지난 뒤에도 이 문서를 읽으면 처음 무엇을 만들고 싶었는지 이해할 수 있어야 합니다.

### ATLAS.md — 지금 어떻게 만들어져 있는가?

개발자와 AI가 읽는 기술 문서입니다.

- 현재 기술 스택과 시스템 구조
- 주요 구성 요소와 연결 관계
- 중요한 동작 규칙과 인터페이스
- 개발을 이어가기 위해 알아야 할 기술적 제약

실제 코드와 일치하는 현재 상태를 설명합니다.

### Handoff — 다음 세션으로 전달하는 임시 기억

Handoff는 영구 문서가 아닙니다.

Plan에서 Design으로, Design에서 Implement로, Implement에서 Deploy로 넘어갈 때 필요한 맥락을 전달합니다.

최종 Deploy에서는 실제 구현과 합의된 내용을 VISION.md와 ATLAS.md에 반영하고, 임시 Handoff를 폐기합니다.

과거 변경 이력은 Git History에 맡깁니다.

# 🧭 세션 시작 프롬프트

아래 프롬프트를 복사해서 해당 환경의 새 세션에 붙여 넣으면 됩니다.

프로젝트에 `AGENTS.md`가 있다면 해당 지침도 함께 적용합니다.

## 1. Plan — 자유로운 구상 💭

**추천 환경:** ChatGPT

아이디어를 자유롭게 이야기하는 단계입니다. 요구사항을 처음부터 정리할 필요는 없습니다.

**시작 프롬프트**

> 지금부터 Spark의 Plan을 진행하자.
>
> 너는 나와 함께 제품을 구상하는 개발 동료야.
>
> 내가 자유롭게 아이디어를 이야기하면 함께 고민하고, 새로운 관점을 제안하고, 필요할 때 반론도 해줘.
>
> 아직 구현이나 문서 작성을 서두르지 말자. 대화 자체가 기획 과정이야.
>
> 충분히 방향이 정해지고 내가 Design으로 넘기자고 하면, 그때 합의된 구상과 중요한 맥락을 Handoff 문서로 정리해줘.
>
> 합의하지 않은 요구사항이나 구현 방법은 임의로 추가하지 마.

**Design으로 넘길 때**

> 지금까지의 대화를 Spark Design으로 넘길 수 있도록 Handoff를 작성해줘.
>
> 제품의 목적, 기대하는 사용자 경험, 합의된 요구사항, 중요한 제약과 아직 결정하지 않은 사항을 담아줘.
>
> 기술적인 구현 방법은 다음 Design 단계에서 코드베이스를 조사하고 논의할 수 있도록 열어 둬.
>
> 이 문서는 다음 개발자가 대화를 이어가기 위한 자료이지, 완성된 설계서가 아니야.

## 2. Design — 기술적인 토론 🛠️

**추천 환경:** Codex

Plan에서 구상한 제품을 현재 프로젝트에 어떻게 구현할지 함께 결정하는 단계입니다.

**시작 프롬프트**

> 지금부터 Spark의 Design을 진행하자.
>
> 먼저 AGENTS.md와 VISION.md, ATLAS.md가 있다면 읽고, 전달한 Plan Handoff를 확인해줘.
>
> 기존 코드베이스를 조사한 뒤, 우리가 만들려는 기능을 어떻게 구현할 수 있을지 나와 토론하자.
>
> 중요한 기술적 선택에는 대안과 장단점을 설명하고 네 의견도 적극적으로 제시해줘.
>
> 나는 개발자이므로 기술적인 이야기를 피할 필요는 없어. 다만 익숙하지 않은 기술은 기존에 아는 개념과 연결해 설명해주면 좋겠어.
>
> 처음부터 완성된 설계문서를 작성하거나 구현을 시작하지 말고, 대화를 통해 합의된 구조를 찾아가자.
>
> 내가 Implement로 넘기자고 하면 그때 Design Handoff를 작성해줘.
>
> 지금은 코드 수정 없이 조사와 토론부터 시작하자.

**Implement로 넘길 때**

> 지금까지 논의한 기술적 결정과 코드 조사 결과를 Spark Implement Handoff로 정리해줘.
>
> 합의한 구현 방향, 중요한 기술적 선택과 이유, 관련 코드 구조, 유지해야 할 동작, 남은 불확실성을 담아줘.
>
> 이 문서는 구현을 돕기 위한 참고 자료야. 실제 구현 중 더 좋은 방법을 발견하면 변경할 수 있고, 중요한 변경은 나와 논의하면 돼.
>
> 구현 단계를 과도하게 세분화하거나 불필요한 추가 작업을 만들지는 마.

## 3. Implement — 실제로 만들기 ⚡

**추천 환경:** Codex

합의된 구상을 실제 소프트웨어로 만드는 단계입니다.

**시작 프롬프트**

> 지금부터 Spark의 Implement를 진행하자.
>
> 먼저 AGENTS.md, VISION.md, ATLAS.md가 있다면 읽고, 전달한 Design Handoff를 확인해줘.
>
> 합의된 제품의 목적과 구현 방향을 바탕으로 실제 코드를 작성해줘.
>
> Design Handoff는 참고 자료이지 절대적인 계약서가 아니야. 더 좋은 구현 방법을 발견하면 나와 논의하면서 변경할 수 있어.
>
> 특히 UI/UX와 창의적인 부분에서는 네가 적극적으로 새로운 아이디어를 제안해도 좋아.
>
> 기존 프로젝트에서 잘 동작하는 부분은 존중하고, 요청하지 않은 기능 추가나 대규모 리팩터링은 하지 마.
>
> 가능한 한 실제로 동작하는 결과물을 보여주고 내 피드백을 받아 개선하자.
>
> 작업 규모에 맞게 검증하고, 실제로 확인하지 못한 부분은 구분해서 알려줘.
>
> 내가 Deploy로 넘기자고 하면 구현 결과와 중요한 변경 사항을 Handoff로 정리해줘.

**Deploy로 넘길 때**

> 이번 구현을 Spark Deploy로 넘길 수 있도록 Handoff를 작성해줘.
>
> 실제 구현한 기능, 기존 설계에서 변경된 사항과 이유, 검증 결과, 아직 확인하지 못한 부분, 빌드·머지·배포에 필요한 정보를 담아줘.
>
> 대화와 Git History에서 확인할 수 있는 불필요한 작업 일지는 반복하지 마.
>
> VISION.md와 ATLAS.md에 반영해야 할 변경 사항도 구분해줘.

## 4. Deploy — 마무리와 전달 🚀

**추천 환경:** Codex

실제 구현 결과를 정리하고 필요한 후속 작업을 수행하는 단계입니다.

**시작 프롬프트**

> 지금부터 Spark의 Deploy를 진행하자.
>
> 먼저 AGENTS.md, VISION.md, ATLAS.md가 있다면 읽고, 전달한 Implement Handoff와 실제 코드 변경을 확인해줘.
>
> 이번 작업의 실제 구현 결과와 합의된 변경 사항을 바탕으로 VISION.md와 ATLAS.md를 현재 상태에 맞게 갱신해줘.
>
> VISION.md에는 제품의 목적과 사용자 경험에 관한 중요한 변경만, ATLAS.md에는 현재 기술 구조와 동작 규칙에 관한 중요한 변경만 반영해줘.
>
> 이후 이번에 요청한 빌드, 머지, 배포, 릴리즈 등의 후속 작업을 수행해줘.
>
> 요청하지 않은 운영환경 변경이나 추가 개선 작업은 하지 마.
>
> 필요한 내용이 영구 문서에 반영되었다면 임시 Handoff를 폐기해줘.
>
> 마지막에는 무엇이 완료됐고 무엇이 남았는지 간결하게 보고해줘.

## ☕ 평소에는 그냥 대화하세요

Spark는 명령어를 외우거나 단계별 절차를 반드시 수행해야 하는 프레임워크가 아닙니다.

"이거 좀 이상한데?"

"이렇게 만들면 더 재미있지 않을까?"

"지금 구조가 어떻게 되어 있어?"

"그냥 한번 만들어 보자."

이런 대화에서 개발이 시작될 수 있습니다.

필요할 때 기술 설계를 깊게 논의하고, 필요한 만큼 구현하고, 실제 결과를 확인하며 다시 발전시키면 됩니다.

작업이 작다면 여러 단계를 건너뛰어도 됩니다. 다만 프로젝트의 방향이나 기술 구조가 실제로 바뀌었다면, 마무리할 때 두 정본에 반영합니다.

**Spark는 개발을 통제하기 위한 절차가 아니라, 개발자가 AI와 함께 더 자유롭게 만들기 위한 약속입니다.**
